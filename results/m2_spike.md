## Review notes (written after the run by code review, not by the runner)

These notes interpret the table above. Every figure they cite is in `results/m2_spike.json`.

1. **The 600 s stereo memory NO is a tie, not a measured fail.** The peaks are 0.3 to 1.4% over a budget of 10^9 bytes, one run each. If the budget means 1 GiB, all three fit. 600 s mono has about 11% headroom.
2. **The 600 s peak is set by how this spike moves data, not by the analysis.** In every phase stereo sits about one float32 channel above mono, so V8 never collected the transferred channels. The final jump of about 260 MB comes within about 400 ms of posting the result, which is one Float32Array per frame cloned while the worker's originals are still resident. If M2.1 drops the channels before analysis and transfers the spectrum as one flat buffer, it would likely use less memory than this. That is not measured.
3. **The WAV rows use decodeAudioData, not the DOM-free WAV parser that spec 4.3 requires.** With the parser, the file's ArrayBuffer stays as JS garbage, so expect up to the file size on top of the peak.
4. **"Analysis fits" counts run plus decodeAll only.** Including decode, mix, spectrum columns and post, 600 s files take about 23 to 27 s end to end, still under the 60 s placeholder.
5. **Conditions:** headless, one run per file, on a machine with heavy swap in use and another session running. phys_footprint counts swapped pages, so swap does not lower the verdict. It may still change when GC runs.
