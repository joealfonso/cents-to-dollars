**User.** The same singer as in M1 (VALIDATION.md section 11): classically trained, practising alone. Her voice type, range, A4, mic and room are still unknown. Joseph runs setup and validation.

## 4. M2.1 Open an audio file and analyse the take

### 4.1 Behavior

- She picks a local file (WAV, MP3, M4A/AAC). The app decodes it, analyses the whole take with the post-take method (MEASUREMENT.md 1.5, `decodeAll` with `lag: Infinity`), and shows pitch over time, cents over time, vibrato over time and the spectrogram.
- The screen must show: file name, duration, the analysis sample rate and how it was obtained (section 4.3), channel count, the method label "Whole take (YIN + continuity)", A4, and the plot(s). Clicking or focusing a time shows that frame's values as text (note, Hz, cents, FLAT/SHARP), so the plot is not the only carrier of the data.
- A4 changes recompute cents and note names without re-analysing. F0 does not depend on A4.
- States: No file; Decoding; Analysing (with progress); Done; Done, no pitch found; Cancelled; Error (could not decode, too long, too large, too short, sample rate not supported, file type not supported, out of memory).
- Leaving the route, or picking another file, cancels any running work and discards its results.

### 4.2 Data flow

1. File object, read locally. No network request carries any of its bytes.
2. Read the file's native sample rate from its header (section 4.3).
3. Decode to channel data at the analysis rate. For WAV, the samples come from a DOM-free WAV parser (section 4.3), not from `decodeAudioData`.
4. Mono = arithmetic mean of all channels per sample, computed in float64, as `tools/wav.ts` does. **FINAL** (parity depends on it).
5. Analysis runs off the main thread (a Worker; engineer's choice of how). It runs a DOM-free module that a Node runner also imports. `src/dsp/` stays free of DOM and Node APIs; worker glue lives outside `src/dsp/`.
6. Output per frame: `t`, `start`, plain-YIN `voiced`, whole-take `f0` (0 when unvoiced), `aperiodicity`, `rmsDb`, band energies, spectrum power 0 to 4 kHz. Plus vibrato windows (section 4.4).
7. Display. Pitch marks are never averaged across frames (averaging hides octave slips, as in DESIGN.md 2.9). If the spectrogram has fewer columns than frames, each column shows the mean power of the frames it covers (**design choice**, stated in the caption).
8. On leave or new file: buffers released, worker work stopped.

### 4.3 Sample rate: how it is learned, and the policy

`decodeAudioData` always resamples to its context's rate and does not report the file's own rate. So the native rate has to come from the file header, and decoding has to happen in a context created at that rate. Resampling does not change pitch; what it changes is the tracker's configuration, which is set in samples (N 2048, W 1024, hop 256) and validated only at 44.1 and 48 kHz. It also breaks exact parity with the Node runner.

**How the native rate is learned.**
- **WAV (FINAL):** a DOM-free parser reads `fmt ` and `data` (PCM 16, 24, 32-bit and float 32, 64-bit, extensible format, any channel count: what `tools/wav.ts` accepts) and returns the rate and samples. No `decodeAudioData`, so no resampling. `tools/wav.ts` keeps working; a Node test checks that the new parser and `tools/wav.ts` return identical samples on every fixture.
- **MP3:** the rate is in the first valid MPEG audio frame header (after any ID3v2 tag). The file is then decoded in a context created at that rate.
- **M4A/AAC:** the rate is in the `esds` AudioSpecificConfig (or the `mp4a` sample entry). HE-AAC with implicit SBR signalling decodes at twice the signalled rate, and that cannot be known from the header. Rule: when SBR or PS is signalled explicitly, use the doubled rate; when the header gives a rate but SBR could be implicit, the label says "File rate not confirmed" and the take is treated as an other-rate file if that rate is not 44.1 or 48 kHz.
- **Any other container, or a header that cannot be parsed:** rate unknown, treated as an other-rate file.
- Browsers must support AudioContext rates of at least 8 to 96 kHz (Web Audio spec); outside what the browser accepts, the file is an other-rate file.

**Rates 44.1 and 48 kHz (FINAL):** analysed at that rate, never resampled.

**Other rates and unknown rates: Q1 DECIDED 2026-11-08, Option B (resample to 48 kHz).** The engineer builds Option B only. Option A stays below for the record and is not built.
- **Option A, refuse (reviewer's lower-cost default for M2.1).** Error state "This file's sample rate ({rate} Hz, or unknown) is not supported yet. Export it at 44.1 or 48 kHz." Resampling can be added later without changing anything else here.
- **Option B, resample to 48 kHz (my recommendation).** Decode in a 48 kHz context, label "Resampled from {rate} Hz to 48 kHz" or "Resampled to 48 kHz, file rate unknown", and validate it with V-07. Reason: at 96 kHz tau_max = N - W = 1024 caps the lowest F0 at 93.75 Hz; at 22.05 kHz W is 46.4 ms, and MEASUREMENT.md 3's attenuation formula predicts about 19% under-reading of a 7.5 Hz vibrato, past the 10% criterion. Resampling to 48 kHz avoids both.

The same policy applies to mic takes in M2.3 (section 6.2). The M1 live view is unchanged and keeps analysing at the device rate, with the 93.75 Hz floor at 96 kHz as an existing known limit (to be stated in MEASUREMENT.md 1.1 by tech-writer).

### 4.4 New measurement: vibrato over time (MEASUREMENT.md new section 12)

- Windows of `VIB_WINDOW_S` = 2.5 s (same as the live view's UI constant), start times every `VIB_STEP_S` = 0.5 s (**design choice**), over the whole-take contour.
- Each window is passed to `analyzeVibrato` unchanged (MEASUREMENT.md 3). Result per window: rate, extent (plus or minus), or "none found", with the window's time span.
- No averaging across windows.
- Known limit, to state in MEASUREMENT.md: a window spanning a note change contains a step in the contour. Behaviour on such windows is not validated; the fixtures below score only windows inside one steady-vibrato section.

Whole-file F0, cents and spectrogram use the existing definitions (MEASUREMENT.md 1, 2, 4). The band ratio (MEASUREMENT.md 5, already defined for a take) may be shown in a Details area, **CUTTABLE**.

### 4.5 Length limits: measurement spike first (task 1 of M2.1)

Browser speed and memory for long files are not measured. The 115 MB figure for 600 s at 48 kHz mono float32 is arithmetic only. Real use can be 2 to 3 times that or more: per-channel decoded buffers (a stereo file is 230 MB before mixing), the float64 mono mix (230 MB at 600 s), any copy into the Worker that is not a transfer, the frames (112,500 at 600 s, each with candidate arrays) and the spectrum columns.

**Spike, before any M2.1 UI work.** In her browser (OPEN Q5), for 48 kHz WAV and MP3 files of 60, 300 and 600 s, mono and stereo, measure: decode time, analysis time (real-time factor in the Worker), and peak memory of the tab (method is the engineer's choice; record which). Output: a results file in `results/` with the numbers and the browser version, plus a short note.

**Limits are set from the spike.** `MAX_DURATION_S` = the longest tested duration that completes within the memory and time budgets, and `MAX_FILE_BYTES` follows from it. The budgets are OPEN Q2; placeholders until then: peak tab memory under 1 GB, analysis under 60 s (**design choices**). The 600 s and 200 MB values from revision 1 are dropped as defaults.

### 4.8 Edge cases (reachable)

- MP3 or AAC priming and padding: times shift by the codec delay relative to the original WAV. Times are relative to the decoded audio; the take view's method note says so.
- Stereo with opposite-phase channels averages to near silence: "no pitch found", correct for the mean signal.
- Variable-rate or damaged MP3s that decode partially: the decoded length is analysed and shown.
- An MP3 whose frames change sample rate mid-file: the first frame's rate is used; the rest is whatever the decoder produces (reported as a known limit, not handled).
- DRM-protected M4A: "could not decode".
- Clipped files: analysed as is. A clipped-sample count is **CUTTABLE** (samples with \|x\| >= 1.0 after decoding).
- Out of memory during decode or analysis: "This file is too large for this browser to analyse".

## 5. M2.2 Reference tones and interval recognition

### 5.1 Behavior

- **Reference tone** (shared by aural skills and Pitch match): plays MIDI note m at f = A_ref x 2^((m - 69) / 12), with A_ref from the A4 setting.
- **Interval recognition** (Tools 02): the app plays two notes; she picks the interval name. She can replay the question. After answering she sees whether the answer matches and the correct name, then moves on. The screen shows "{correct} of {answered}" for this visit only.
- Settings (each a **design choice** default, final values OPEN Q7): intervals m2 to P8 (12 names, tritone as one name "Tritone"); ascending, descending, or harmonic (both notes at once); lower note in MIDI 60 to 72 (C4 to C5) with both notes inside MIDI 48 to 84; tone 1.0 s, gap 0.3 s.
- States: Ready, Playing, Waiting for answer, Answered, Audio error (no output device, AudioContext failed).
- The first tone starts inside a click (user gesture). No mic is used; the mic indicator stays off.

### 5.2 New definitions (MEASUREMENT.md new sections 15 and 16)

- **Tone (15).** Frequency as above. Waveform OPEN Q6 (**design choice** default: partials 1 to 6 with amplitude 1/k, which carries better than a sine on small speakers). Peak level <= -12 dBFS for one tone and for the sum of two (**design choice**). 20 ms raised-cosine onset and offset ramps, as in `py/synth.py`. Rendered at the AudioContext's own rate (no rate conversion between generator and output).
- **Interval recognition (16).** k = m_upper - m_lower, 1 to 12. The generator draws k uniformly from the enabled set and the lower note uniformly from the allowed notes. An answer matches when the chosen k equals the asked k. Count = matches out of answered questions this visit. Not an acoustic measurement.
- **Output path accuracy.** The digital tone frequency is set by the generator. The acoustic frequency adds only the device sample-clock error: 100 ppm is 0.17 c (VALIDATION.md 7). Speaker and room do not change frequency.

### 5.3 Acceptance criteria

| # | Where | Criterion |
|---|---|---|
| T-01 | N | For every MIDI 48 to 84 and A_ref in {440, 442}, the requested frequency equals A_ref x 2^((m - 69) / 12) to 1e-9 relative. |
| T-02 | N or B (5.4) | Rendered at 44.1 and 48 kHz, every such tone's frequency, measured by an estimator independent of YIN (for example a least-squares fit of the fundamental's phase), is within 0.1 c of requested (**design choice**). |
| T-03 | N or B (5.4) | Same renders through `FrameAnalyzer` plus whole-take decode: median F0 within 0.5 c of requested (**design choice**, above the tracker's measured P95 of 0.23 to 0.37 c on sines), 0 octave errors. |
| T-04 | N or B (5.4) | Peak absolute sample of one tone and of any harmonic-mode pair is <= 10^(-12/20). |
| T-05 | N or B (5.4) | First and last sample of each tone are 0, and the envelope matches a 20 ms raised cosine to 1e-6. |
| T-06 | N or B (5.4) | Tone length equals the requested duration to within 1 sample at the render rate. |
| T-07 | B | The tone plays at the AudioContext's rate (asserted for 44.1 and 48 kHz contexts). |
| T-08 | N | With a seeded random source, the question sequence is identical on every run. |
| T-09 | N | Generator uniformity, chi-square goodness of fit (arithmetic below). For each of seeds 1 to 20, 12,000 questions with all 12 intervals enabled give X^2 = sum over intervals of (count - 1000)^2 / 1000 < 31.26, the 0.999 quantile of chi-square with 11 degrees of freedom (alpha = 0.001 per seed). |
| T-10 | N | No generated question has a note outside MIDI 48 to 84 or a lower note outside the configured range. |
| T-11 | B | Replay plays the same two frequencies and does not change the count. |
| T-12 | N | Answering k when k was asked increments both numbers of "{correct} of {answered}"; a different answer increments only "answered". |
| T-13 | B | Leaving the route stops any playing tone within one render quantum of the leave resolving, and resets the count. |
| T-14 | B | Changing A4 changes the frequencies of the next question, not the one in progress. |
| T-15 | B | No `getUserMedia` call is made on the interval recognition screen. |
| T-16 | B | When the AudioContext cannot start, the Audio error state is shown and no question is counted. |

**T-09 arithmetic.** Each interval's count is binomial with n = 12,000 and p = 1/12: mean 1,000, SD = sqrt(12000 x (1/12) x (11/12)) = sqrt(916.7) = 30.3. Revision 1's band of plus or minus 50 is 1.65 SD; two-sided, a fair generator falls outside it with probability about 0.099 per interval, so about 1 - 0.901^12 = 0.71 of seeds would fail at least one of 12 intervals (treating them as independent). The chi-square test uses all 12 counts at once. At alpha = 0.001 a fair generator fails a given seed with probability 0.001, so 20 seeds fail with probability about 0.02. Because seeds are fixed, the outcome is deterministic per seed list; if a fair generator happens to fail a listed seed, that is reported, and the seed list is not edited to make it pass. An equivalent alternative, if preferred: plus or minus 4 SD = plus or minus 121 per interval (two-sided p = 6.3e-5 per interval, about 7.6e-4 over 12).

### 5.5 Edge cases

- Bluetooth output: large output latency delays the tone, not its frequency. Section 6.4 measures it for Pitch match.
- Laptop speakers roll off at low frequencies (not measured here); a C3 sine may be nearly inaudible. The harmonic default reduces this.
- Output device changes mid-question: the next tone plays on the new device; no error unless the context fails.
- Hidden tab: playback continues; the question does not advance on its own.

### 6.1 The set

| Exercise | Status | Input | Why |

### 6.2 Data flow for every exercise

1. Mic through Phase B `live.ts` (owner `exercise`). The live readout during singing is plain YIN, as everywhere live.
2. The capture path keeps the raw input samples in memory, each with its AudioContext sample-frame index (the worklet's `currentFrame` of its input block, as `tracker.worklet.ts` already uses for `start`). Not MediaRecorder: lossy encoding would change the measurement.
3. Sample rate: the policy of section 4.3 applies to the exercise context. 44.1 or 48 kHz device rate: captured as is. Other rate under Option A: the exercise does not start ("Your audio input runs at {rate} Hz. Exercises need 44.1 or 48 kHz."). Other rate under Option B: the exercise's AudioContext is created at 48 kHz, so the browser resamples the input, and the result is labelled "Resampled from {rate} Hz".
4. After the take, the M2.1 module runs the whole-take method on the captured samples. **Every exercise measure comes from the whole-take result, never from the live frames.** The result says "Measured after the take (whole take)". The live trace and the result can differ, including by an octave (VALIDATION.md Q6).
5. Results shown until the next take or leaving the route. Nothing stored.

### 6.3 New measurement definitions (MEASUREMENT.md new sections 13, 14, 17)

All parameters below are **design choices**, kept as named constants in one file, and written to `summary.json` under `m2_params` so the UI never copies them.

**Hold segment (13.1), shared.**
- Runs: maximal sequences of voiced frames of the whole-take contour, with unvoiced gaps of up to 3 frames bridged (the rule in `vibrato.ts`). The longest run by duration is chosen; on a tie, the earliest.
- Trim: drop frames with t < t_first + `ONSET_TRIM_S` (0.25 s) or t > t_last - `RELEASE_TRIM_S` (0.10 s).
- Valid if the trimmed span is at least `MIN_HOLD_S` (E1: 1.0 s; E2: 0.5 s). Otherwise "No sustained note found".
- Statistics use voiced frames inside the trimmed span only; bridged frames are not used.
- Median of an even count = mean of the two middle values.

**E1 Sustain (13.2).** Target: a note she picks (MIDI n, f_T = A_ref x 2^((n - 69) / 12)), or none, in which case f_T is the nearest equal-tempered note of the median F0.
- **Hold duration (s)** = t_last - t_first of the chosen run, before trimming.
- **Centre offset (c)** = median over hold frames of 1200 log2(f / f_T). Negative is FLAT.
- **Drift (c/s)** = (median cents of the last third of the trimmed span - median cents of the first third) / (2D/3), with D the trimmed span and thirds split by time. Medians, not a line fit, so a partial vibrato cycle does not tilt it.
- **Vibrato** = `analyzeVibrato` on the hold frames (MEASUREMENT.md 3, unchanged).
- If \|centre offset\| > 50 c, the result also names the nearest note of the median ("Nearest note: G4"). No judgement word.
- Sources: the split between accuracy (centre offset) and stability is used in singing research, for example Dalla Bella, Giguere and Peretz (2007), JASA 121(2), and Pfordresher et al. (2010), JASA 128(4). **Not checked.** They motivate the idea only; no parameter or threshold is taken from them.

**E2 Pitch match (14).**

*Timing.* The tone and the capture run in one AudioContext, so both are indexed in context sample frames (frame = context time x fs).
- The tone is scheduled to start at context frame s_on and end at s_off.
- Sound the context emits at frame s reaches the capture buffer at frame s + L_rt, where L_rt is the round-trip latency: output latency, plus acoustic travel, plus input latency.
- `outputLatency` is not reported by every browser (Safari and Firefox at the time of the review), `baseLatency` understates Bluetooth delay, and no browser reports input latency. So **L_rt is measured on her setup by the speaker and microphone check (section 6.4), never taken from those properties.**
- Tone interval in the capture = [s_on + L_rt, s_off + L_rt]. Sing window = [s_off + L_rt + `GUARD_S` x fs, that + `SING_S` x fs], with `GUARD_S` 0.3 s and `SING_S` 4.0 s.
- **If the check found the speaker below the voicing gate** (headphones, the normal case): there is no leak to avoid and L_rt cannot be measured acoustically. The window starts at s_off + `GUARD_S` x fs, and `SING_S` is extended by `LATENCY_MARGIN_S` (0.5 s), so a long output delay (Bluetooth) shifts her singing later inside the window, not out of it. The leak flag is still computed.

*Measures.*
- Hold segment per 13.1 with `MIN_HOLD_S` 0.5 s, on the whole-take analysis of the sing window only.
- **Interval to reference** c = 1200 log2(f_med / f_R), with f_med the median hold F0.
- **Octave displacement and match offset** by a wrap function: k = floor(c / 1200 + 0.5) (ties go up), offset = c - 1200 k, so offset lies in [-600, +600). k is reported as a number of octaves ("an octave below" for k = -1); k = -0 is shown as 0. Whether an octave-displaced match is accepted is not judged (OPEN Q10).
- **Sound during the reference** (leak flag): over the tone interval as captured, from s_on + L_rt + 0.05 s x fs to s_off + L_rt, the share of whole-take-voiced frames. Flag if the share >= `LEAK_VOICED_FRAC` (0.2). Sub-flag "matches the reference" if the median F0 of those frames is within 50 c of f_R x 2^j for some integer j. Wording is neutral: "The microphone picked up sound while the reference played" and, with the sub-flag, "It may be hearing the speaker. Headphones avoid this." The trial is still reported.
- Why this protocol: capture runs with echo cancellation off (`capture.ts`), so a speaker tone reaches the mic. The app never scores while the tone plays, the guard covers room decay after the measured latency, and the leak flag says when the speaker is the likely source. A sung note that copies the reference cannot be told apart from leakage inside the sing window; the guard is the only protection there. Headphones are recommended on the screen.

**E4 Sing an interval (CUTTABLE, 14.2).** As E2 with target f_R x 2^(s/12); c, k and offset computed against that target.

**E3 Range sweep (CUTTABLE, 17).** Over the whole-take contour, every 0.3 s window (`RANGE_WIN_S`, stepped by one frame) in which all frames are voiced and P90 - P10 of the cents is <= 150 c (`RANGE_SPREAD_C`, wide enough for a plus or minus 50 c vibrato) qualifies, labelled with the nearest note of its median. **Lowest and highest held note** = lowest and highest qualifying label, each with the time it occurred, so she can check it against the spectrogram. Known risk: an octave-down tracker error held for 0.3 s produces a false low note. The result says "Check the lowest note by ear"; there is no automatic correction.

### 6.4 Speaker and microphone check (prerequisite for E2; MEASUREMENT.md section 14.3)

Promoted from revision 1's CUTTABLE acoustic tone check. Pitch match cannot start until this check has run in the current visit with the current input and output devices. A `devicechange` event, or a change of the selected device, invalidates it. Whether the result may be remembered across visits is OPEN Q15.

*Procedure.* With the mic owned by `live.ts` (owner `speakercheck`), schedule `CHECK_BURSTS` = 5 reference tones (the E2 timbre and level, 0.4 s each, 0.6 s apart) at known context frames s_i, and capture the input with frame indices.

*Measures.*
- **Onset per burst:** the first captured frame after s_i at which the RMS over 1 ms exceeds the median 1 ms RMS of the 200 ms before s_i by 20 dB (**design choices**). L_i = onset frame - s_i.
- **Round-trip latency L_rt** = median of the L_i over detected bursts, in samples and ms. Spread = max - min of the L_i.
- **Leak level (dBFS)** = RMS of the captured signal from onset + 0.1 s to onset + 0.3 s, median over detected bursts.
- **Verdict words (no judgement):** "The microphone hears the speaker" if at least 3 of 5 bursts are detected and the leak level is at or above the voicing gate (-50 dBFS); "The microphone does not hear the speaker" if no burst is detected; otherwise "Inconclusive, run again".
- If spread > 50 ms (**design choice**), L_rt is reported with a warning and E2 uses the largest L_i instead of the median.
- **CUTTABLE extra:** frequency offset of the captured bursts, measured as in calibration (MEASUREMENT.md 8). Reported, no threshold.

### 6.7 Edge cases (reachable)

- Octave slip in the whole-take result during a hold: the median can land an octave off, shown as a large offset plus "Nearest note". Low misreads are the likelier direction (VALIDATION.md 4.4).
- She starts before the sing window: those samples are not scored; the leak flag may fire.
- She sings two notes in the window: the longer run is scored.
- Headphones with a mic that still picks them up faintly: leak level below the gate gives "does not hear the speaker"; above it, L_rt is measured.
- Output switched to Bluetooth after the check: `devicechange` invalidates the check (E-27). If the browser fires no event, the check result is stale; the screen says the check applies to the devices in use when it ran.
- Mic denied, missing or ended: DESIGN.md 3.0 states apply.
- Another route owns the mic: `live.ts` ownership rules apply (one owner).
- Device rate other than 44.1/48 kHz: section 6.2 step 3.
- Singing below -50 dBFS: unvoiced, "No sustained note found", with the existing gate hint during the take.
